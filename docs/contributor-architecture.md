# Distribution architecture rules

- Remote asset updates use manifest-to-manifest deltas only when the running server exposes the trusted helper. The helper locally clones, patches, completely validates, and atomically swaps the candidate. Never mutate the active tree in place.
- Exact asset-manifest matches perform zero uploads and zero restarts. Keep full bundles authoritative and retain full deployment for compatibility fallback. Never add Pterodactyl per-file comparison loops to the normal path; deep remote verification is diagnostic-only.

- Linux x86-64 uses a native process-scoped `LD_PRELOAD` library. Wrapper mode is canonical; managed executable replacement is compatibility-only.
- Read-only features default on. Every state-changing or gameplay QoL feature owns an off-by-default gate and must not initialize native work when disabled.
- `ZANIK_ENABLED` is the master runtime gate. When false, the canonical launcher must execute the verified official binary without `LD_PRELOAD` or any Zanik runtime initialization while preserving installation and persistent data.
- `FEATURE_QOL_AUTO_COMPOST` is a reserved, incomplete feature and must remain false until its native integration, compatibility gates, diagnostics, performance evidence, and development-server validation are complete.
- New native or operational dependencies must update compatibility analysis, runtime validation, diagnostics, backups, reports, positive/negative tests, and safe feature-local failure behavior.
- Hooks and dispatchers are latency-critical: no I/O, waits, unbounded scans, or blocking locks on the game thread. Observe per-operation timing, queue depth, drops, cache state, and slow calls; preserve the aggregate tick budget.
- Storage administration uses an asynchronous, independently gated native pipeline. The HTTP worker must discover storage, capture index/serial identities, resolve catalogs and recipes, check capacity, and build immutable plans. The game-thread dispatcher may execute at most one precomputed native action per eligible tick, revalidating the world and every actor, inventory, controller, item, and item-data identity first. Move and organize jobs roll back one action per tick; partial deletion must be reported explicitly. Each operation family owns compatibility, timing, and a 1 ms circuit breaker. `POST /api/admin/storage/mutate` returns a session-bound request ID for `GET /api/admin/storage/mutation-status`; neither endpoint may expose native identifiers. Current-build support stays fail-closed until every action and rollback path passes development-server timing, combat, transition, and whole-mod A/B validation.
- Game assets and containers never enter Git or core releases. Linux dedicated-server containers are inventory-only. The self-contained Windows client tool owns mapping generation, targeted extraction, catalog generation, reviewed drift checks, full/multipart packaging, and atomic server activation.
- Never broaden extraction to the complete cooked tree. Keep recipes versioned and restricted to runtime catalogs plus artwork reachable from Zanik's web application. Treat `.usmap`, raw exports, generated bundles, and temporary UE4SS files as local game-derived data.
- Building images come from the `DisplayIcon` package selected by the cooked building record. Export ordinary textures, embedded `GeneratedIcons` thumbnails, and procedural thumbnails directly with UnrealAssetScout using full package paths. Do not introduce Blender, custom model rendering, or reconstructed world-model thumbnails without new evidence and a separately reviewed architecture change.
- Resolve every explicit item `Icon` reference by its full cooked package path; authored textures are not required to use a `T_Icon_*` basename. World resources without direct `ItemData` must use reviewed stable actor-to-harvested-item identities, and missing resource art must fail extraction rather than create a placeholder.
- When corrected artwork replaces a web asset at an existing public path, revise the URL embedded in static HTML/CSS so previously cached responses cannot mask the activated file. Validate the rendered page reference as well as a fresh direct request for the asset.
- The fixed nodestone map marker is Zanik-authored artwork, not a cooked game texture. Keep its full-resolution transparent master under `asset-tools/artwork/`, derive the reviewed 256x256 map PNG from that master, package only the derivative with the extractor, and include the derivative in the `map-icons` generation contract. Do not introduce a model exporter or runtime renderer for this marker.
- Fixed-nodestone admin teleporting must use the reflected `ASwitchableTeleporter::PerformTeleport` named-location wrapper with an identity-validated paired target prepared off the game thread. Do not replace it with raw coordinates, `AActor::TeleportTo`, or the player-built lodestone GUID bypass. Keep its compatibility, timing counters, and circuit breaker independent so public nodestone markers remain available when mutation is unsafe.
- Operational JSON crossing the Windows PowerShell/Python boundary must be written as UTF-8 without a BOM and read with legacy BOM tolerance. Test the boundary with Windows PowerShell 5.1 as well as PowerShell 7; Python-authored fixtures alone are insufficient.
- Never infer recipe availability from the absence of a provider. Export all base and plugin progression tables, preserve only the reviewed unknown-trigger identities, and fail closed on additional unresolved-route drift.
- Treat cooked QuestData as a versioned asset schema. Keep legacy `ObjectiveTexts` and current `Objectives[].Value.Description` decoding centralized, and require reviewed counts for quest shells, objective descriptions, step states, and markers. Top-level quest counts alone are never sufficient compatibility evidence.
- Player recipe and quest tracking require the shared bounded game-thread query dispatcher even when every mutation feature is disabled. Install that dispatcher only when a dependent tracker or administration feature is enabled; keep all mutation queues dormant behind their independent gates and report dispatcher compatibility separately for both read-only trackers.
- Recipe and quest catalog-object discovery and compatibility retries belong on the worker loop. The shared game-thread dispatcher may execute only already-resolved, bounded single-object queries; tracker startup or a partially streamed catalog must fail closed without scanning the Unreal object array from the hook.
- Journal Windows extraction stages and retain a validated generated-tree checkpoint after packaging failure. Cleanup must be Python-owned, bounded, and restricted to marked Zanik workspaces; a post-validation cleanup warning must not invalidate the bundle.
- Temporary mapping generation must refuse pre-existing loader collisions, never force-kill the client, recover from its journal before new work, and verify that every touched client path is restored.
- A bundle with unreviewed catalog drift is a candidate marked `incompatible`; installers must reject it until the profile is reviewed. Build-ID differences alone are informational.
- Treat broad UnrealAssetScout raw-export counts as reviewed minimum coverage, not exact catalog identity: regenerated mappings can resolve additional packages from unchanged cooked containers. Exact generated catalog counts, schemas, cross-references, artwork coverage, and fingerprints remain fail-closed. A verified JSON-only checkpoint must resume remaining exports instead of repeating the expensive JSON pass.
- Preserve completed UnrealAssetScout workspaces as private local incremental caches. Persist a structural inventory of catalog selectors and reachable texture targets for every reviewed recipe fingerprint. With an unchanged client, make zero exporter calls for unchanged selector groups, export only additions, and delete only retired outputs that no current target still references. Independently fingerprint generated groups by generator, authored rules, relevant raw inputs, dependencies, and output digest. Seed from a fully hash-validated prior bundle, remove only dirty groups' owned outputs, regenerate only those groups, then run complete validation over the assembled final tree. “Complete regeneration” means producing and validating a complete final bundle; it does not require rerunning unaffected catalog generators. A changed game executable requires broad discovery and conservative generation across the bounded recipe because existing package contents may have changed. Never upload, publish, or place raw cache files or mappings inside the server bundle.
- Keep `asset-tools/extraction-recipe-history.json` synchronized with every published recipe hash. Its `jsonTargets` must compose the exact public `jsonFilter`; this is what lets an older completed cache migrate to a new recipe without rescanning unchanged selector groups.
- Recipe snapshot migration uses stable recipe IDs and the generated catalog history. Across a reviewed catalog change, removed IDs are filtered from saved responses and newly introduced IDs remain unknown until a live rescan; an unknown historical fingerprint still fails closed.
- The full ZIP and Pterodactyl parts must assemble to the same file/hash tree. Part installation rejects missing, unexpected, corrupt, duplicate, traversal, and symlink entries before atomic activation.
- Keep remote development loops tight. Validate and hash complete bundles locally, verify uploaded archives once, trust successful ZIP extraction and CRC checks, and remotely check only critical or changed files plus representative entries before activation. Do not download and hash every remote asset during normal deployment. Deep Doctor should hash the tree on the server and download one aggregate report; preserve per-file API downloads only as a last-resort fallback for older installations, suspected corruption, or user-requested audits.
- Keep clean-clone tests asset-free. Validate every release archive after clean extraction for layout, modes, checksums, credentials, raw game files, operator files, and research data.
- Maintain `.tmp/distribution-implementation.md` during distribution work; it is local, ignored, and must never be committed.
- Treat `VERSION` as authoritative and publish stable releases only from matching protected `vMAJOR.MINOR.PATCH` tags. Tagged archives must pass clean extraction and checksum validation before durable publication.
- Use GitLab Generic Packages and Releases as the authoritative permanent binaries; pipeline artifacts are handoff and secondary retention only. Mirror source refs and new stable release assets to the public GitHub repository only after their GitLab push/publication succeeds. Never add release, GitHub, or CurseForge credentials to Git or job output.
- Maintain an ignored `.tmp/release-implementation.md` checklist while changing release automation.
- Maintain an ignored `.tmp/windows-extractor-implementation.md` checklist while changing or validating the Windows asset pipeline.
- Zanik Manager is a portable PySide6 Windows application. Keep hosting operations behind the provider interface, keep Pterodactyl credentials exclusively in Windows Credential Manager, and make every remote mutation journaled, hash-verified, recoverable, and explicitly scoped to one selected server.
- Every Zanik-managed remote backup must contain non-secret ownership/family/state metadata. Retain one verified recovery point per family, protect unresolved operations, remove successful staging and transient reports, and never clean world saves, panel backups, live `zanik-data`, active assets, user uploads, pinned bundles, or unrecognized paths.
- The manager archive embeds the exact server ZIP and the file-identical extracted contents of the Windows asset-tool ZIP published beside it. Release validation must prove both payloads and reject credentials, game assets, mappings, raw exports, operator files, or developer-machine paths.
- Treat Manager release freshness and installed server-payload freshness independently. Compute the server contract only from operational server paths; Manager/docs-only changes must not create a false server update, while any operational payload change must change the contract.
- Maintain an ignored `.tmp/windows-manager-implementation.md` checklist while changing or validating the manager.
