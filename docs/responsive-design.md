# Responsive interface architecture

Zanik responsive layouts are based on available space and input capability, not device names or user-agent detection. The shared shell publishes `window.ZanikResponsive`, root `data-responsive-mode` and `data-coarse-pointer` attributes, visual-viewport dimensions, safe-area variables, and a `zanik:responsive` event. Components consume those signals instead of maintaining private phone lists.

## Shared contracts

- Respect `--app-safe-top`, `--app-safe-right`, `--app-safe-bottom`, and `--app-safe-left` whenever a surface touches a viewport edge.
- Use `--app-viewport-width` and `--app-viewport-height` for interfaces affected by mobile browser chrome or the software keyboard. Do not assume `100vh` is the visible Safari viewport.
- Global navigation, the shared header, and ordinary page controls normally have a minimum `--app-touch-target` of 44 CSS pixels. Short landscape uses a deliberate two-rem bottom-navigation row because its persistent vertical cost otherwise overwhelms the map canvas; safe-area inset remains additive. The compact map separately uses the 33-pixel `--map-control-size` density token for persistent map-local launchers, fields, and zoom controls. Repeated previous/next destination controls use the smaller `--map-cycle-control-size` in both desktop and compact layouts, and segmented finder tabs use a 27-pixel mode switch; these adjacent controls do not need the chrome of isolated primary actions. Do not apply the map-specific density tokens to the shared shell.
- Reserve `--site-bottom-nav-h` wherever compact fixed navigation shares a viewport with page content or a page-owned sheet.
- Use semantic buttons, links, tabs, toolbars, dialogs, and labels. SVG icons are decorative when an accessible name is supplied by the control.
- Honor reduced-motion preferences and preserve keyboard access, focus visibility, Escape dismissal, and logical focus return.

## Surface behavior

Desktop pages may use independent floating panels when space permits. Compact layouts coordinate substantial surfaces so only the active finder, player list, settings surface, detail surface, or overlap chooser occupies constrained space. Portrait layouts prefer bottom sheets; short landscape layouts prefer side sheets. Opening one substantial surface closes competing surfaces instead of relying on z-index ordering.

Compact controls use density tiers rather than one phone layout stretched across every screen. The 320-pixel and iPhone SE classes reduce visible padding, type, chip chrome, map-local control size, and sheet height. Modern and large phones may expose more rows because they have more map height. Map-panel launchers belong immediately above the compact bottom navigation; opening Players or Finder hides only the competing launcher, while settings and zoom controls remain available. Keep launcher labels concise on compact screens and place selection detail inside the sheet instead of truncating it in the launcher.

Compact Finder and Online Players sheets have exactly one scrolling region: their list content. In portrait bottom sheets, the opaque title and drag handle remain anchored above it; a slow vertical drag continuously adjusts sheet height within the safe area, a full or fast downward swipe closes it, and a normal tap retains the native open/close behavior. Short-landscape side sheets retain the same anchored opaque boundary but omit swipe handles because their height is fixed between the shared header and navigation. Do not attach sheet resizing to the list because that would compete with content scrolling.

Touch scrolling inside a compact detail sheet must take priority over map dragging. A touch gesture beginning in a scrollable quest detail pans that sheet and cannot dismiss it; mouse dragging over non-interactive tooltip copy may continue to pan the map. Use pointer-type-aware routing rather than disabling either behavior globally.

The compact global shell uses a single-row top bar and safe-area-aware bottom navigation. Short landscape tightens that navigation to the text plus modest padding; portrait uses the normal 44-pixel-class touch row rather than desktop-like vertical padding. World, Players, Highscores, and Recipes remain one tap away. Diagnostics, UI size, Admin sessions, and authenticated logout live in the shared More surface. `zanik:site-surface` coordinates that surface with page-owned sheets.

Every site page advertises the same web app manifest and Apple home-screen metadata. The manifest owns the stable app identity, standalone display mode, full-site scope, theme colors, 192- and 512-pixel Android/Chromium icons, maskable icon purpose, and `/` start URL so installing from any page launches the Online home page without browser chrome; Apple also receives its dedicated 180-pixel touch icon. Keep these endpoints available in maintenance mode and do not couple the authored application icons to the licensed generated-asset bundle.

Admin claim links remain in scope and request navigation into an existing installed app where the browser supports link capture. Do not assume a browser can detect or launch an installed Home Screen web app: iOS may open the link in Safari, whose session container is separate. The claim page must therefore leave the token unredeemed until the user chooses the browser or securely copies the existing single-use token into the app's anonymous **More → Admin login** form.

Map focusing uses a safe map rectangle: the visible canvas after subtracting the shared header, compact toolbar, safe areas, and any open sheet. Initial result focus may use a bounded compact zoom; previous/next marker navigation preserves zoom and pans within the safe rectangle. UI scaling must not change map coordinates, marker geometry, or the underlying image transform.

Map gesture state must explicitly hand off between pointer counts. When either finger ends a two-finger pinch, rebase the remaining finger to the current rendered center and scale before permitting one-finger panning; never reuse its pre-pinch drag origin. The handoff counts as movement so ending the remaining pointer cannot activate a marker that happened to land underneath it. Apply the same transition to the world map and embedded quest maps.

The world-map stage commits at most one normal two-dimensional transform per animation frame, and the final pointer release synchronously flushes the newest state. Do not force its complete desktop surface into a compositor layer with `translate3d`, `will-change: transform`, `backface-visibility`, or equivalent promotion hints: mobile WebKit may allocate the promoted surface at the unscaled dimensions instead of the selected image tier and exhaust its graphics budget during ordinary panning. Gesture constraints use viewport dimensions cached at initialization or resize so routine pointer movement does not repeatedly query layout. Resource, NPC, quest, player, lodestone, and nodestone coordinates remain normalized percentages, and any visible detail is repositioned only as part of the committed frame.

Compact layouts use a 1024-by-1024 CSS map surface. Marker coordinates remain the same normalized percentages used by desktop, while each marker is independently quarter-scaled to retain equivalent screen size without applying CSS `zoom` to an entire overlay plane. This keeps source icons sharp and prevents WebKit from rasterizing another oversized layer. Pan, zoom, reset, focus, resize, and popup calculations must use the active visual-surface size rather than assuming 4096 CSS pixels. Desktop retains the 4096-pixel surface.

Compact resource markers retain their original PNG sources, automatic image interpolation, depletion opacity, hit targets, and canonical positions at every map-image tier, but do not apply CSS `drop-shadow()` per icon. Hundreds of simultaneous filtered images force WebKit to allocate and repaint an offscreen effect for each visible marker, producing a middle-zoom performance cliff even though the underlying icon bytes are already decoded and cached. Removing that effect is not an icon-resolution reduction. If dense marker sets still exceed the frame budget without filters, use bounded tiled marker batching rather than lowering source image quality or restoring an oversized full-map surface.

Compact NPC markers follow the same no-filter rule without losing their state language. Preserve the original icon and opacity, then draw the state color as a bounded radial background behind the marker: red for hostile, green for non-hostile, yellow for quest or inactive, brighter green for ready, and white for dead or unloaded. This keeps classification and runtime state visible at every zoom while avoiding alpha-shaped multi-shadow filters on every NPC image. Desktop may retain the richer filtered treatment where the graphics budget permits it.

Compact manual pinch and button zoom use the same 18-times ceiling as mobile marker focusing. Desktop retains the 32-times ceiling.

Map visual detail follows rendered pixel density without changing that geometry. The base image switches among 1024-, 2048-, and 4096-pixel generated derivatives; the 2048 tier is preloaded so initial API and catalog work cannot starve the first compact zoom. Region labels use a small set of ordinary text elements in the canonical coordinate system. In compact mode their viewport-sized container is a sibling of the transformed map stage. Each label is shaped once at a fixed two-times text and outline resolution; committed map frames update its screen position and a small element-level compositor scale from the same pan, zoom, and active-surface values used by markers. Do not change actual font or outline sizes during zoom because fractional glyph re-hinting visibly morphs the lettering, and do not use a transformed or animated SVG because mobile Safari may cache it at degraded quality either during a gesture or after the gesture becomes idle. Independent high-resolution text elements preserve exact map positions and stable, sharp active and idle rendering without a large canvas allocation. Compact devices are capped at the 2048 map-image tier to stay within mobile browser memory budgets. At the lowest detail tier, expensive marker shadows are simplified because those effects are smaller than a displayed pixel. Resolution changes use hysteresis and run only after dragging or pinching has been idle; repeated renders do not restart the pending upgrade timer.

Static map images, generated icons, fonts, and static finder catalogs use browser validators and a bounded freshness lifetime. The map finder reads saved selection IDs before loading data, then fetches the large Resource, NPC, or Quest catalogs only when its active tab or visible saved markers require them. Live players, constructed lodestones, nodestones, and selected spawn state remain independently polled and uncached.

Map detail cards use the same coordinated-surface model. Portrait mode presents them above the bottom navigation; short landscape mode uses a left side sheet and leaves map controls on the opposite edge. Details retain a compact close control, while quest details also provide a Back action that restores the Quest Steps Finder instead of discarding that navigation context. Primary identity and actions stay visible, secondary location text belongs in an expandable section, and changing orientation or visible browser height preserves the open detail, selected marker, map center, and relative zoom.

## Migration and validation

New responsive work belongs in shared shell variables and reusable surface, toolbar, tab, and icon-button patterns whenever another page can consume it. Page-specific media queries describe genuine component behavior rather than duplicate global viewport or safe-area detection. Prefer container queries when a component's own width is the governing constraint.

Validate at minimum 320×568, 375×667, 390×844, 430×932, 568×320, 667×375, 844×390, 768×1024, and representative desktop sizes. Exercise 50%, 100%, and 150% UI scale, portrait/landscape transitions, coarse and fine pointers, dynamic browser chrome, the software keyboard, scrolling sheets, focus movement, reduced motion, and horizontal-overflow and overlap invariants.

Rendered-browser validation should use a current Chromium build through its DevTools protocol against a locally built Zanik listener. The standard map matrix checks responsive-mode selection, page overflow, shell target sizes, toolbar/control separation, and map/nav boundaries. Interaction coverage opens competing surfaces, cycles a multi-marker quest objective, rotates portrait to landscape, and reduces the visible viewport height while asserting that the detail surface, selected marker, and relative map zoom survive. The representative-page matrix covers Online, Players, Highscores, Recipes, Diagnostics, and the public Admin login shell at compact portrait, short landscape, tablet, and desktop widths for all three supported UI scales. Keep this rendered validation in addition to the JavaScript and HTTP shell tests; source-token assertions cannot detect computed-layout overflow.

For an authenticated Admin page, use the existing HTTP authentication fixture rather than weakening the browser target. An anonymous request to `/admin/sessions` must remain a JSON `401`; `/admin/claim` supplies the public Admin shell for anonymous rendered-layout coverage.
